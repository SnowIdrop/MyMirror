# 十二、上游可见访问身份的一致性

## 用户要求（本轮验收补充，不改变原六阶段目标）

目标：同一个上游会话的页面、接口、媒体及实时通信，应具有稳定且相互兼容的网络出口、浏览器特征和认证上下文。不能仅修改 User-Agent 就宣称浏览器指纹一致。

- 明确会话执行上下文，绑定上游账号、认证会话、出口配置及客户端特征配置；不得在不同请求中随机切换。
- 检查 HTTP、资源下载、WebSocket，以及实际采用的语音通信路径是否使用预期出口。不得因浏览器直连而意外暴露另一套访问来源。
- 分别检查服务端连接特征与浏览器 JavaScript 可见特征，包括 UA/Client Hints、平台、语言、时区及相关浏览器能力；不能把请求头一致等同于完整指纹一致。
- Cookie、认证刷新、设备或会话标识保持正确关联；不得跨用户串用，也不得把账号凭据发送到无关静态资源域名。
- 重连、刷新、重启及出口故障时明确哪些特征保持、哪些可能变化；不得静默切换身份或自动重放生成请求。
- 浏览器执行环境、网关传输客户端与出口策略必须作为整体评估。若普通反向代理无法满足目标，先报告具体差异及架构取舍，不能不断堆叠伪装脚本来掩盖问题。
- 不擅自将产品改为远程浏览器方案；涉及架构变化时，说明对现有界面、语音、文件、性能和多人隔离的影响，再取得方向确认。
- 网络身份一致性不能合并不同用户的资源权限。
- 验收分别记录“已验证一致”“存在可解释差异”“尚未验证”；不能承诺上游绝对无法识别代理。真实账号验证仍须授权。

### 判定口径

- **已验证一致**：只对明确列出的输入、已运行路径和观察层成立，例如合成请求确实经过指定本地出口。必须列命令、输入、字面输出/退出码和证据，不把源码意图升级为运行验收。
- **存在可解释差异**：有源码或运行证据支持的不同层、不同路径行为；写清当前是否可达、是否违背目标、是否必须修复或由用户确认架构取舍。可解释不等于已接受或通过。
- **尚未验证**：没有充分运行证据、尚未实现或未开放的路径、实际部署出口、TLS/HTTP2特征、真实浏览器/语音环境等。保持门禁，不能把“没有请求”当作“身份一致”。

纯回环探针不得继承未经确认的公网代理配置；所有账号/密钥使用合成值，独立DB/端口/输出，只清理自己进程。页面/API/媒体/实时通信最终需按同一上下文验收，但独立用户的Rust ACL仍分别执行。原四角色和历史三态保持不变，新增记录只扩展证据。
